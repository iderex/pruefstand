# The case file format

This answers issue #2. It fixes what shape a case takes, which fields it carries,
what a reader is meant to do with each of them, how the format is versioned and
what happens to a published number when the version moves.

It does not fix units, frames or the inertia parameterisation, which is #13. It
does not implement the schema, the reader or the content hash, which is #31. It
does not decide which quantity a class is judged by, which is #7, nor how the
reference answer is produced, which is #9.

It is written before any case file exists. `cases/` holds a README and nothing
else at the commit this note landed in:

    git ls-files cases/
    cases/README.md

That ordering is the whole point of the issue. Every case in this suite, every
adapter that translates one, every result record that names one and every number
on the report card inherits whatever this decision gets wrong, and by the time
the first case is written the cost of changing it is already paid twice.

## The decision

A case is data. It is not code, and it is not data with an indirection to code.

Three shapes were on the table and the argument between them is about what a case
has to survive rather than about what is convenient to write.

Data is inspectable without running anything, diffable, publishable as a dataset
somebody who never runs this suite can cite, and refusable by a schema. What it
cannot express is a case whose initial condition is the result of a computation,
and there are such cases: a torque-free top placed deliberately near its
separatrix has an initial condition that comes out of solving for a modulus, not
out of somebody's judgement.

Code expresses anything and gives up all four of those properties at once. It is
also the shape that makes a case quietly non-reproducible, because the case then
depends on the version of everything the generating code imported.

The hybrid, data with a named and versioned generator standing in for the fields
that must be computed, keeps the expressiveness and costs two artefacts that have
to be kept in step. A reader holding the file does not hold the case.

What this decision takes is the data shape with the third one's problem solved in
the file rather than beside it. **A computed value is written into the case file
as a literal, and the generator that produced it is recorded as its provenance.**
The file is complete on its own: a reader, a schema, a diff and a citation all see
the number. The generator is a reproduction route and a check, never a
substitute for the value, so there is nothing to keep in step at read time and
exactly one thing to re-run when somebody doubts the number.

The cost is real and is paid in the other direction: a value regenerated by a
newer generator and not written back is a file that lies about its own
provenance. That is a check somebody has to write, it is not written here, and
#31 is where it lands.

## The means

TOML, read with `tomllib` from the standard library.

The means question is asked per artefact rather than carried over, so it is
answered here rather than inherited from the language decision.

It carries the three rules. A missing or malformed field is refusable by a schema
(#31), a refusal is provable by a fixture that trips it, and every number in a
case file arrives with a provenance entry that says where it came from.

Nothing outside this repository forces a format. Case files are read by this
suite and published as data for other people, and no engine, index or catalogue
requires a particular encoding of them.

It adds no language, runtime or dependency. `tomllib` is in the standard library
and this tree already reads TOML:

    git grep -l tomllib
    tests/test_two_test_sets.py

    python -c "import sys, tomllib; print(sys.version.split()[0], tomllib.__spec__.origin)"
    3.14.6 <python install>\Lib\tomllib\__init__.py

Measured on the machine this note was written on, at 3.14.6. Not measured at the
interpreter floor: 3.12 is not installed here.

    py -3.12 -c "import tomllib"
    Python 3.12 not found!

The gate workflow pins the interpreter to the floor, so the floor is exercised on
the server and not on this machine, and what it exercises is whatever the suite
reads rather than this claim in particular.

What TOML costs, stated rather than glossed: the standard library reads it and
does not write it. Anything that generates a case file has to emit the text
itself or take a dependency, and that cost falls on the generator rather than on
the suite, which only ever reads.

Floats are IEEE 754 binary64 and a decimal literal comes back as the value its
shortest representation names:

    python -c "import tomllib; t = tomllib.loads('a = 0.1'); print(repr(t['a']), t['a'] == 0.1)"
    0.1 True

That is one value through one parser and it is not a statement about every
literal a case will carry. A case needing a bit-exact initial condition writes a
literal whose shortest representation is itself, and checking that is #31's.

The alternatives, and where each one stops:

JSON is in the standard library in both directions and has a schema language with
implementations. It carries no comments, which matters less than it looks like
because the reasoning in a case file belongs in named fields a schema can require
rather than in comments a schema cannot see. What decides against it is that the
schema language is only an advantage if the dependency that evaluates it is
taken, and refusing a field with a reason a person can act on is a validator this
project writes either way. Without that dependency, JSON is TOML with worse
ergonomics for a file somebody writes by hand.

YAML is not in the standard library, so the most-published artefact of this
project would be read through a dependency, and its implicit typing has produced
exactly the failure this suite exists to detect: a value that is silently the
wrong type rather than an error. A benchmark format is the last place to accept
that trade.

Python is refused by `cases/README.md`, which says the directory holds no Python,
and the reason there is the same one as here.

The suites that already exist test it. A case file is bytes read by `unittest`
tests from a bare interpreter, and no parallel apparatus is needed.

## The fields

Every field below is required unless it says otherwise. What a reader is meant to
do with it is the second half of each entry, because a field nobody knows what to
do with is a field that gets filled in to satisfy a schema.

### The file

`format`, an integer. The version of this format, not of the case.
A reader that does not implement this version refuses the file by version rather
than by discovering a missing field.

`id`, a string. The stable identifier of this case, unique across `cases/`.
Result records name it, the report card renders it, and it is never reused for a
different physical system. A case whose physics changes gets a new `id`, because
a published number naming the old one would then be about something else.

`title`, a string, one line. What a person calls this case.

`class`, a string. Which class of system this case belongs to.
The class decides which questions may be asked of the case at all. A trajectory
comparison is legitimate for one class and meaningless for another, and the
report card refuses an aggregate across classes. Which classes exist and which
metric each admits is #7 and is not fixed here.

`convention`, a string. The identifier of the units, frames and inertia
parameterisation document this file is written against.
Every number in the file means what that document says and nothing else. A reader
that does not implement the named convention refuses the file rather than
guessing. The vocabulary of legal values is #13's, and until #13 lands there is no
legal value, so no case file can be added to `cases/` yet. That is deliberate:
the dependency is mechanical rather than a note somebody has to remember.

`summary`, a string. What this case is and what it is for, in prose.
This is what a reader who is not going to read the numbers takes away, and it is
where a case says which effect it exists to show.

### `[horizon]`

`seconds`, a float. How much simulated time the case runs for.

`why`, a string. Why that is long enough to show the effect.
A reader checks this against the timescale of the effect rather than trusting the
number. A rattleback horizon shorter than one reversal period, or a drift horizon
shorter than the drift, is a case that cannot answer its own question, and the
reason is where that becomes visible.

### `[[body]]`, one or more

`id`, a string, unique within the file. What the initial condition, the
constraints and the geometry refer to.

`mass`, a float.

`inertia`, in the parameterisation the named convention fixes.
Not restated here. #13 fixes what this contains, including the rule for principal
axes that the rattleback needs, and a second statement of it in this document is
the drift that rule exists against.

`[[body.geometry]]`, one or more per body. The geometry that touches the world:
its kind, its dimensions and its placement relative to the body.
This is the surface a contact can occur on. A body with no geometry touches
nothing, which is legitimate for a torque-free top and is a defect for a rolling
disk, and the difference is visible only because the field is required rather
than optional.

### `[initial]`

Per body, the state at time zero, given exactly: the placement, the orientation,
the velocity and the angular velocity, in the representations the convention
names.

There is no approximately here. A reader reproduces the state, and a case that
describes its initial condition instead of stating it is a case two people will
start differently.

### `[[constraint]]`, zero or more

`kind`, a string. The constraint the case intends, in physical terms, naming the
bodies and surfaces it holds between.

`holds`, a string. When and where it holds.

A reader takes this as what the case asks for. How any particular engine is asked
to provide it, and what evidence is recorded that it was honoured, is #12 and
lives in that engine's adapter. No engine's parameter name appears in a case
file, and `cases/README.md` already carries that rule.

### `[contact]`

`model`, a string. The contact and friction model the case intends, in physical
terms.

`dissipation`, a string. Which dissipation model the case intends, or the
explicit statement that it intends none.

Required, and required even when the answer is none, because the two cases in
this suite that only do the interesting thing because of dissipation are the two
where a default would be invisible. The reference refuses a dissipative case
naming no model rather than filling one in, and which model each of those cases
names is #50.

### `[measured]`

`quantity`, a string. The name of the quantity this case is judged by.

`units`, a string.

`why`, a string. Why that quantity is the right question for this case.

A reader hands this to the metric estimator, which computes exactly this and not
a proxy for it. Which quantities are legitimate per class is #7.

### `[reference]`

`kind`, one of: the answer is a closed form, the answer is computed by this
project's own reference, or the answer is tabulated from a source.

`statement`, a string. For a closed form, which solution; for a computed answer,
that it is computed here and by what; for a tabulated one, which table and where
it came from.

`bound`, a string. The error bound on the reference answer, or the statement that
the bound is computed with the run.
A reference answer carrying no bound is refused, which is #49. The field is
required here so that the refusal has something to read.

### `[tolerance]`

`value`, a float. `units`, a string.

`why`, a string. The derivation.
A tolerance with no derivation is a number somebody chose after seeing a result,
and this field is what makes that visible in a diff. A reader checks the
derivation against the reference's own bound: a tolerance tighter than the bound
is a tolerance that measures the reference.

### `[[provenance]]`, one or more

`field`, a string. The dotted path of the value or values this entry covers.

`kind`, either sourced or chosen.

`citation`, required when sourced. Where the value came from, precisely enough
that a reader can check that the tippe top being simulated is a tippe top
somebody actually described.

`why`, required when chosen. Why this value, given that nobody published it.

The rule over this table is that every numeric value in the file is covered by
exactly one entry. That is what makes an invented parameter visible instead of
absent: a case that made up its inertia says so, with the reason, in the file
that publishes it. Checking the covering is #31's.

## The list above is a second source of truth, and it is temporary

This document fixes the fields, so today it is the source. When #31 lands the
schema, the schema is the authority for which fields exist and this document
keeps the reasons, pointing at the schema for the list.

Between now and then there are two statements of the field set and they can
drift. That is a defect this document creates rather than one it inherits, it is
the shape `restated-not-referenced` names, and #31 is what closes it. Naming it
here is not the same as fixing it.

## The version field, and published numbers

`format` is an integer. It is raised when a change would make an existing file
mean something different or stop being readable, and not for an added optional
field that older files can omit.

What happens to published results when it moves is decided by what a result names
rather than by a migration. A result record names the case `id`, the `format` it
was read at and the content hash of the case file it ran against, and #31 defines
that hash while #10 fixes the record.

So a published number is never rewritten and never relabelled. Raising a case
file's `format` changes its content hash, which makes every published number
naming the old hash visibly about a different file rather than silently about
this one. A number for the new file comes from running the case again. That is
the whole rule, and its cost is that the report card carries results against more
than one hash of the same case until everything is re-run, which is a cost worth
paying because the alternative is a number whose provenance moved underneath it.

A file whose `format` a reader does not implement is refused by version. That is
the difference between "this suite is too old for this case" and a stack trace
about a missing key, and it is why `format` is the first field.

## One worked case, end to end

The torque-free asymmetric top, which is #52. Written out so the shape can be
argued before anything depends on it.

**This example cannot be copied into `cases/` and pass.** Its `convention` names
nothing, because #13 has not fixed the vocabulary yet, and there is no legal value
for that field today. The numbers below are therefore shape and not physics: what
they mean is exactly what #13 will say they mean, and this document declines to
say it first.

    format = 1
    id = "torque-free-asymmetric-top-generic"
    title = "Torque-free asymmetric top, generic orbit"
    class = "integrable"
    convention = "unset-pending-13"
    summary = """
    A rigid body with three distinct principal moments, in free rotation with no
    applied torque. The spatial angular momentum and the energy are constants of
    the motion, so drift in either is drift the integrator introduced. The orbit
    is placed away from the separatrix, so the elliptic modulus is bounded away
    from one and the closed form is evaluated where it is well conditioned.
    """

    [horizon]
    seconds = 100.0
    why = """
    The body-frame motion is periodic and one period at this initial condition is
    a little over two seconds, so the horizon carries roughly fifty periods. An
    energy drift per period below the tolerance is invisible over one period and
    obvious over fifty, and fifty is where a drift small enough to be plausible
    still separates from rounding.
    """

    [[body]]
    id = "top"
    mass = 1.0
    inertia = { xx = 1.0, yy = 2.0, zz = 3.0 }

    [[body.geometry]]
    kind = "none"
    why = "Nothing touches the world in this case; the body is in free rotation."

    [initial.top]
    placement = [0.0, 0.0, 0.0]
    orientation = "identity"
    velocity = [0.0, 0.0, 0.0]
    angular_velocity = [1.0, 0.3, 0.7]

    [contact]
    model = "none"
    dissipation = "none"

    [measured]
    quantity = "relative drift in the spatial angular momentum vector"
    units = "dimensionless"
    why = """
    The spatial angular momentum is exactly conserved by the continuous system,
    so any change in it over the horizon was introduced by the integrator. It is
    a vector rather than a scalar, so its drift carries a direction as well as a
    size, which is what #56 asks the report card to render.
    """

    [reference]
    kind = "closed-form"
    statement = """
    The Jacobi solution for the free asymmetric top: the body angular velocity
    components are elliptic functions of time with a modulus fixed by the energy
    and the angular momentum. Evaluating it is #44.
    """
    bound = """
    The evaluation is in binary64 and its accuracy is stated as a bound by #44.
    The bound is a property of the evaluation, not of this case.
    """

    [tolerance]
    value = 1e-9
    units = "dimensionless"
    why = """
    Placeholder. The tolerance is derived from the reference's own bound and from
    the resolution ladder, neither of which exists: #44 states the bound and #11
    fixes the ladder. A number written here before those exist would be a number
    chosen to make a result pass, which is what the `why` field is for catching,
    so this case says so rather than inventing a derivation.
    """

    [[provenance]]
    field = "body.top.inertia"
    kind = "chosen"
    why = """
    Any three distinct principal moments give an asymmetric top, so there is
    nothing to source. These are spread widely enough that the intermediate axis
    is unambiguous and the motion is not near the symmetric limit.
    """

    [[provenance]]
    field = "initial.top.angular_velocity"
    kind = "chosen"
    why = """
    Chosen so the orbit sits away from the separatrix, where the elliptic modulus
    approaches one and the closed form is ill conditioned. The separatrix case is
    a second case rather than a second initial condition in this one, because a
    case is judged at one tolerance.
    """

    [[provenance]]
    field = "horizon.seconds"
    kind = "chosen"
    why = "Fifty periods, for the reason in the horizon's own field."

Two things this example is meant to make arguable. The `tolerance.why` field is
carrying an admission that the tolerance is not derived yet, which is the field
doing its job rather than a hole in the format: a case that cannot justify its
tolerance says so in the artefact somebody reads. And every number in the file is
covered by a provenance entry saying it was chosen rather than sourced, which is
the honest answer for this case and would be a defect in the tippe top.

## What refuses a bad case

Nothing yet. The schema, the reader that returns either a fully validated case or
an error naming the field, and the content hash are #31, and the check that
refuses a case missing a required field is that issue's first done-when.

Said plainly because the issue this document answers asks for the check to be
named rather than for it to be assumed: at this commit a case missing any field
above is refused by a reviewer, which is not a mechanism.

## What is not decided here

- Units, frames, the orientation representation and the inertia parameterisation,
  and therefore what any number in a case file means: #13.
- The schema, the reader, the content hash and the first case files: #31.
- Whether a case is physics rather than merely a well-formed document, which is a
  different refusal from a missing field: #32.
- Which metric each class admits, and what the class vocabulary is: #7.
- How the reference answer is produced and how far it is trusted: #9.
- How a rolling constraint is asked of an engine that cannot express it, and what
  evidence is recorded that it was honoured: #12.
- Which dissipation model each dissipative case names: #50.
- The resolution ladder every case is run at, and therefore half of every
  tolerance derivation: #11.
- What a run records about the case it ran: #10.

## The mark

PROSE, NOT ENFORCEMENT, whole document. Nothing in this tree reads this file and
nothing refuses a case file that departs from it, because there is no case file
and no reader to refuse one. The mechanism is owed and #31 holds it.

Two narrower absences, named so a green is not read as covering them. Nothing
checks that the field list above and #31's schema agree once both exist, which is
the drift this document names against itself. And nothing checks that a value
regenerated by a newer generator was written back into the file it came from,
which is the cost the decision above accepts in exchange for the file being
complete on its own.
